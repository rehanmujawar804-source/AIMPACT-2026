## 1. Goal and Non-Goals of the Hackathon MVP

### 1.1 MVP Goal
Build a functional, source-traceable, evidence-first web application that investigates **short-delivery / quantity discrepancy disputes** between small Indian B2B suppliers and buyers.

The application must accept a dispute message and relevant commercial records (Invoices, Dispatch Records, Proof of Delivery/Receipts, Payments, Credit Notes), verify discrepancies using deterministic code, validate that all numbers and references match actual records, display findings strictly mapped to the 4 canonical states, and enable human review before any conclusion is accepted.

### 1.2 Explicit Non-Goals (Scope Boundaries)
To ensure delivery within 8 hours, the following are strictly excluded:
- **No full ERP/Accounting replacement:** ProofTrail does not create ledgers, issue invoices, or submit GST tax filings.
- **No automated legal adjudication or fraud claims:** The system never accuses parties of fraud, bad faith, or theft.
- **No direct communication/collections CRM:** ProofTrail does not automatically send emails, WhatsApp messages, or demand notices.
- **No heavy external infrastructure:** No external relational/NoSQL databases, vector databases (Pinecone/Weaviate), message brokers (Redis/Celery), Docker multi-containers, or blockchain ledgers.
- **No document OCR pipeline:** ProofTrail operates on structured JSON fixtures representing parsed records. Raw PDF/image OCR is out of scope.
- **No open-ended chatbot:** No arbitrary "chat with your invoices" floating conversational window.

## 2. Canonical Finding States (Non-Negotiable)

Every material finding generated by the application must use one of the four approved states defined in `docs/04_DATA_CONTRACTS_AND_ARCHITECTURE.md`:

```text
┌─────────────────────────────────┬────────────────────────────────────────────────────────┐
│ Canonical Finding State         │ Semantics & Meaning                                    │
├─────────────────────────────────┼────────────────────────────────────────────────────────┤
│ SUPPORTED_BY_RECORDS            │ The statement is directly confirmed by supplied data.  │
│ CONFLICTING_RECORDS             │ Supplied records actively contradict each other.       │
│ NOT_FOUND_IN_PROVIDED_DATA      │ The record/data is absent from the uploaded dataset.   │
│ UNRESOLVED                      │ Ambiguity or insufficient evidence prevents conclusion.│
└─────────────────────────────────┴────────────────────────────────────────────────────────┘
```

> [!IMPORTANT]
> Prohibited states: `FRAUD`, `GUILTY`, `PROVEN`, `CORRECT`, `CHEATING`.  
> An absence of a record in the dataset must never be presented as proof that the event never occurred in reality.

## 7. Definition of Done (DoD) for the Hackathon MVP

The ProofTrail hackathon MVP is considered **DONE** only when all of the following criteria are satisfied:

### 1. Functional Integrity
- [ ] A user can select or enter a short-delivery dispute and submit it.
- [ ] The system accurately compares Invoice, Dispatch, and Signed Receipt quantities.
- [ ] Financial reconciliation accurately calculates: `Invoice Amount - Payments - Approved Credits = Balance`.
- [ ] Findings strictly use the 4 canonical states.
- [ ] Every finding cites valid `source_record_ids` present in the provided dataset.
- [ ] If records are missing (e.g. no credit note, missing receipt), the status is `NOT_FOUND_IN_PROVIDED_DATA` or `UNRESOLVED`, never an accusation of fraud.
- [ ] If the LLM is disconnected or errors, manual claim entry and deterministic verification continue to work flawlessly.

### 2. Code Quality & Test Coverage
- [ ] TypeScript compiles cleanly with 0 type errors (`npm run typecheck`).
- [ ] Vitest test suite passes with 100% green tests (`npm test`).
- [ ] Next.js production build succeeds (`npm run build`).
- [ ] No secrets, `.env` files, or API keys are committed to Git.

### 3. Truthful Evaluation & Presentation
- [ ] Evaluation results are derived from actual observed script runs across labelled synthetic cases.
- [ ] No fabricated claims (e.g., no claims of "99.9% market accuracy" or "patent-pending AI").
- [ ] The presentation clearly articulates why deterministic code owns verification while AI assists with interpretation.

## 8. Observed Results & Evidence Discipline Rule

All team members must follow these strict communication rules:
1. **Never invent metrics:** Do not write "Evaluated on 100 enterprise invoices" when we evaluated on 4 synthetic test cases.
2. **Explicit Denominators:** Always report exact numbers: `"Evaluated on 4 synthetic test cases: 4/4 passed deterministic verification, 3/4 passed zero-shot extraction."`
3. **Absence in Data ≠ Absence in Reality:** If a credit note is absent, the UI must say `"No credit note found in supplied records"`, NOT `"Supplier never issued a credit note."`
4. **AI is an Assistant, Not an Authority:** AI extracted fields must be labeled `"AI-extracted · Reviewable"`. AI never creates source records or generates authoritative calculations.
